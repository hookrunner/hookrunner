# Main deployment and PR previews

The Go service runs on the ARM64 VPS as an ordinary user. Actions builds an
ARM64 server and matching browser client, uploads a tar.gz bundle, polls for
readiness, and updates one PR comment. No Docker, SSH credentials, domain, or
HTTPS is required. Main is available at **`http://YOUR_VPS_IP:20000/`**;
PR previews use free ports in **20001–20100**. Each port serves both the page
and the proxied WebSocket connection, with no query parameter needed.

## VPS setup

Install Go 1.24+ and `bubblewrap` using your distribution's packages. Builds use
the VPS's system libraries; use Ubuntu 24.04 ARM64 (or a system with compatible
glibc/libgcc) to match the Actions runner. Unprivileged user namespaces must work.
The service fails a deployment if bwrap cannot create its sandbox; there is no
unsandboxed fallback.

From the repository on the VPS:

```sh
mkdir -p "$HOME/.local/bin" "$HOME/.config/hookrunner"
(cd deploy/previewd && go build -o "$HOME/.local/bin/hookrunner-previewd" .)
cp deploy/preview.env.example "$HOME/.config/hookrunner/preview.env"
chmod 600 "$HOME/.config/hookrunner/preview.env"
```

Edit that environment file: set `PREVIEW_IP` to the VPS's actual public IP and
replace `PREVIEW_TOKEN` with a token generated by `openssl rand -hex 32`.
`PREVIEW_IP` is configured explicitly, not detected by the service; it is the
address printed in the startup log and included in returned preview links.
For a private repository, set `PREVIEW_GITHUB_TOKEN` to a read-only GitHub token
that can read this repository's pull requests and contents. It stays on the VPS.
Public repositories can omit it, but authenticated requests avoid the lower
anonymous GitHub API rate limit. This token is not passed to game processes.

Allow inbound TCP **8080** and **20000–20100** in the VPS/cloud firewall, or
change `PREVIEW_LISTEN`, `PREVIEW_MAIN_PORT`, and `PREVIEW_PORTS` to ports you
prefer. The main port must be outside the PR range and free when previewd
starts. For PRs, the service skips occupied ports and holds each HTTP listener
open while deploying.
Game server ports are assigned separately on loopback and need no public rule.

Run as your unprivileged user, with no init-system dependency:

```sh
set -a
. "$HOME/.config/hookrunner/preview.env"
set +a
export PREVIEW_DATA="$HOME/.local/share/hookrunner-previews"
exec "$HOME/.local/bin/hookrunner-previewd"
```

The binary stays in the foreground and writes service logs to stderr. Run it
under your existing supervisor or an OpenRC service if you want it to survive
logout/reboot. It handles SIGINT/SIGTERM itself and bwrap terminates game
processes if previewd dies. The Go binary reads environment variables; it does
not load the example environment file itself.

## GitHub setup

Under repository **Settings → Secrets and variables → Actions**, set:

- Repository variable `PREVIEW_API_URL`: `http://YOUR_VPS_IP:8080`.
- Repository secret `PREVIEW_TOKEN`: the same deployment token as on the VPS.

The workflow uses `ubuntu-24.04-arm` and the pinned Rust toolchain in this repo.
Your GitHub plan/repository must support that runner. It deploys same-repository
PR branches; fork PRs are deliberately excluded. The build job has read-only
GitHub permissions. A separate comment job has `pull-requests: write` and
does not check out or execute PR code.

Rust dependencies for both the ARM64 server and WASM client, Cargo downloads,
and installed Cargo tools are cached with `Swatinem/rust-cache`. A matching
cached `wasm-bindgen` is reused without reinstalling. The project's own crates
are rebuilt so changes to gameplay, maps and build fingerprints take effect.
Cache keys track the Rust toolchain, manifests, lockfile and compiler settings.
The cache is saved even if deployment later fails.

`main.yml` ("Deploy main") builds and deploys every push to `main`, including
merges, and warms the same cache so new PRs can restore a base-branch cache.
You can also run it manually with the `main` branch selected. The first run
is cold; until a base-branch cache exists, each new PR needs its own initial build.

The main HTTP listener stays on `PREVIEW_MAIN_PORT` (default **20000**).
Until the first deployment it returns 503. During an update, the working game
continues running; once the new server is ready, requests switch to it and the
old process and player connections are stopped. Failed or stale deployments
leave the working version running. Only the current main head can deploy.
Main does not expire and does not count toward `PREVIEW_MAX`.

If a PR was already open when you installed this workflow, push another commit
or close/reopen it to trigger its first preview. New pushes and force pushes both
redeploy. A ready replacement closes the previous HTTP listener and kills its
bwrap process, including game descendants and existing player connections.
The free port can change; the PR comment is updated with the new URL.
If the replacement fails, the previous preview continues running. Older commits
are rejected by checking the current PR head at upload and publication time.

Closing or merging a PR cancels pending deployment and kills its preview.
Previews also expire after `PREVIEW_TTL` (default 24 hours), with a one-minute
cleanup interval. A maximum of five PRs run concurrently by default. Restarting
previewd stops all games, including main; rerun "Deploy main" and the PR Actions
jobs to recreate them. Job
history is in memory. Logs are capped at 1 MiB per game and available in each
`build-*` directory until that preview is removed.

## Sandbox

Only the game process runs in bwrap. Its filesystem contains the read-only
server binary, `/usr`, `/lib`, and `/lib64` system libraries and the dynamic
linker's cache (`/etc/ld.so.cache`), an isolated
`/proc`, minimal `/dev`, and disposable `/tmp`. There are no home/config/data
mounts and no inherited credentials. User, PID, IPC and UTS namespaces are
isolated, capabilities are dropped, and bwrap kills descendants if its parent
dies. The launcher pins its spawning OS thread for the process lifetime so
parent-death behavior also works correctly with Go.

The host network namespace is shared so the Go service can reach the server's
loopback WebSocket listener. This is filesystem/process isolation, not network
isolation or a per-preview CPU/memory limit. Use trusted team PRs. The public API
requires the deployment token; public game pages do not. HTTP is intentional
for this development setup.

## API

Every API request needs `Authorization: Bearer TOKEN`.

- `POST /deployments?pr=123&sha=FULL_HEAD_SHA`: upload the bundle as the raw
  request body; returns `202` with an `id` and `status`.
- `POST /deployments?branch=main&sha=FULL_HEAD_SHA`: deploy the current main
  commit on the fixed port, using the same bundle format and job polling.
- `GET /deployments/ID`: returns `queued`, `deploying`, `ready` (with `url`),
  `failed` (with `error`), `superseded`, `deleted`, or `expired`.
- `DELETE /previews/123`: stops an existing/pending preview. The PR must be
  closed so a delayed cleanup cannot delete a reopened PR's new preview.

Repeated uploads of the same currently deployed or queued commit reuse its job.
Bundles are limited to 256 MiB compressed / 512 MiB expanded, contain only
regular files and directories, and must include an ARM64 ELF server. Archive
links and traversal paths are rejected. To build a bundle manually on Linux
ARM64, install the matching `wasm-bindgen-cli` version from `Cargo.lock` and run
`./scripts/build-preview.sh`; the result is `dist/preview.tar.gz`.
